States: `unchecked`, `source-consistent`, `candidate`, `confirmed`, `fixed`, `unrecoverable`. “Source-consistent” means no source-level contradiction found; it does not prove semantic parity.

## Candidates and resolutions

Add one entry per distinct suspected root cause, including compiler path, Fission path, counterexample, first wrong stage, test, fix, and verification result.

### C1 — `GETIMPORT` constant operand truncated in lifted IR (`fixed`)

`Compiler.cpp:2900-2912,3009-3022` emits `LOP_GETIMPORT` in AD format with a constant-table index `D` up to 32767, plus an AUX import path. `BytecodeLifter.cpp:489-496` stores `GetABCOperand(B)` in lifted operand 1. This preserves only one byte of the index. AST source reconstruction at `ASTLifterExpressions.cpp:320-346` uses AUX and does not read operand 1, so observable decompilation may survive; lifted IR is inaccurate when import constant index exceeds 255. Need first confirm emitted high-index import is compiler-reachable, then write a BytecodeLifter regression and fix one operand decode.

**Red/green:** Compiler-generated source with 270 distinct string constants and a final `math.pi` emits a `GETIMPORT` with raw D=274. Lifted IR reported 18 (low byte) before fix. Regression asserts decoded IR constant index equals raw D; `BytecodeLifter` now reads `GetD()`. Focused test passes (7 assertions, GCC Debug). Full suite pending.

### C2 — `DUPTABLE` template shape versus reconstructed field insertion order (`source-consistent`)

Compiler `compileExprTable` builds one template from record keys and last values; dynamic fields become nil placeholders, then emitted stores in source order (`Compiler.cpp:2695-2845`). Fission seeds the exact template keys and constant values as literal fields (`ASTLifterExpressions.cpp:752-772`). Crucially, it immediately returns from `LiftTableLiteral` for nonempty `DUPTABLE`, so it **does not fold later stores into that literal**. Subsequent stores remain statements in bytecode order. Recompiled literal preserves template key slots and dynamic stores remain after it. Original insertion-order concern was based on overlooking the early return; no demonstrated divergence. Keep table row open for `NEWTABLE`/`SETLIST` semantics.

### C3 — `FASTCALL3` register operands written through immediate union member (`confirmed`)

Compiler encodes second/third argument registers in AUX bytes (`Compiler.cpp:811-917`); `math.clamp(x, lo, hi)` reaches this opcode (`Builtins.cpp:160-161`, `Compiler.cpp:1460-1480`). `BytecodeLifter.cpp:1072-1091` marks lifted operands 3/4 as `Register` but writes `value.imm.n` rather than `value.reg`. `LiftedOperand` uses a union (`BytecodeLifter.hpp:100-115`), so SSA and validation read an inactive member. On the current little-endian host, the low byte matches the register value; ordinary compiler-produced tests pass before a fix. UBSan has no active-union-member check, and big-endian bytecode reading already fails in `BinaryReader`, so no meaningful red test is available in this toolchain. No observed source-output divergence. Correct the two writes when a reliable check is available, or document a narrow exception to the red-test rule before fixing this representation defect.

### C4 — numeric `for` CFG jump targets appear one instruction early (`source-consistent abstraction`)

Compiler `compileStatFor` emits `FORNPREP` targeting the instruction after `FORNLOOP`, and `FORNLOOP` targeting the first body instruction (`Compiler.cpp:4277-4346`). `BytecodeBuilder::patchJumpD` stores `target - source - 1` (`BytecodeBuilder.cpp:610-638`); VM adds `D` after incrementing `pc` (`VM/src/lvmexecute.cpp:2529-2571`). Fission preserves raw `D` for both opcodes (`BytecodeLifter.cpp:1030-1048`) and `ControlFlowAnalyzer::GetJumpOffset` deliberately uses raw `D` as a pointer-relative offset (`ControlFlowAnalyzer.cpp:53-70`), routing prep's failed check through the latch and the latch back through prep. `BytecodeLifter.cpp:1660-1680` explicitly increments prep offset when the shorthand does not land on matching `FORNLOOP` (e.g. jump threading). SSA comments and liveness (`SSABuilder.cpp:222-248`) treat prep reads as entry-only and omit them on latch edges. This is a CFG abstraction, not a missing `+1` fix. Still assess whether folded/trampolined loops violate its assumptions, but do not modify offset unconditionally.

### C5 — legacy type encoding v1 skips extra bytes (`fixed`)

Current `BytecodeBuilder::writeFunction` emits type encoding v3, but Fission accepts v1-v3. Luau VM's v1 decoder copies `typesize` bytes, then advances by exactly `typesize` (`VM/src/lvmload.cpp:392-428`). Fission copies `typeSize` but advances by `headerSize + typeSize` (`Deserializer.cpp:104-127`); the synthetic v2 header exists only in memory. Valid v1 blobs with type metadata should lose their instruction-count prefix and fail or misparse. This is outside current compiler output but inside declared version support. After audit, make a small v1 bytecode fixture through existing builder/manual encoding, prove red, then correct advancement.

**Red/green:** `LegacyTypeEncodingRegression.cpp` builds a v12/type-v1 blob with a two-byte function type and one `RETURN`. Luau VM accepts and executes it; Fission returned no decoded bytecode before fix. Deserializer now advances over `typeSize` only after copying into its synthetic v2-compatible buffer. Focused test passes (4 assertions, GCC Debug). Full suite pending.

### C6 — generic `FORGLOOP` SSA omits state/index reads (`fixed`)

Compiler `compileStatForIn` initializes generator/state/index at `A..A+2` and emits `FORGLOOP` (`Compiler.cpp:4348-4457`). VM's `FORGLOOP` reads all three (`VM/src/lvmexecute.cpp:2704-2808`). Fission recorded only explicit A; liveness and SSA implicit uses omitted A+1/A+2. A compiler-produced generic loop proved this in a red regression: no `FORGLOOP` implicit-use entry. SSA now records all three reads before its control and loop-variable writes; the SSA oracle models matching VM reads. Latch-carried control phis also required `FORGPREP` to use its entry-edge value, and ASTLifter to recognize the original nil control initializer. Focused test is green (7 assertions); full CTest passed 628/628 and sample stress passed 22/22 after formatting.

### C7 — dead-local rewrite treats global reads as effect-free (`fixed`)

Compiler does not remove a nonconstant `local unused = global` at O1: `areLocalsRedundant` requires constant locals (`Compiler.cpp:4045-4070`), so it emits `GETGLOBAL` or `GETIMPORT`. Fission `DeadLocalEliminator::IsPure` returned true for every `IdentifierExpressionNode`, including `GlobalIdentifier` with `bIsGlobal=true` (`DeadLocalEliminator.hpp:116-124`, `ASTLifterShared.hpp:13-18`), and `RewriteStatements` dropped unread pure declarations (`DeadLocalEliminator.hpp:27-43`). Luau GETGLOBAL may invoke the environment's `__index` metamethod and raise or mutate state; GETIMPORT may resolve dynamically after environment invalidation.

**Red/green:** `CompilerLiftingAuditRegressions.cpp` compiles `local unused = watched; print('after')` and runs both bytecodes under an environment `__index` that prints on `watched`. Before fix, original trace was `"read watched"; "after"`; decompiled trace only `"after"` because generated source discarded the declaration. `DeadLocalEliminator::IsPure` now permits identifier reads only when `bIsGlobal` is false. Focused test passes after fix (4 assertions, GCC Debug). Full suite pending.

### C9 — self-assignment and short-circuit rewrites erase global access effects (`fixed`)

`SelfAssignmentEliminator::IsSelfAssign` removed `x = x` using only equal identifier names (`SelfAssignmentEliminator.hpp:26-34`). `ShortCircuitChainFolder::IsSelfAssign` and `IsTriviallyDeadIf` did the same for bare names (`ShortCircuitChainFolder.hpp:114-133,201-219`); its chain fold also merged two assignments by name (`:33-52,163-199`). These checks did not distinguish local from `Identifier::bIsGlobal`. Compiler emits `GETGLOBAL; SETGLOBAL` for `x=x`, and Luau environment metamethods can run on both.

**Red/green:** `watched = watched; print('after')` under `__index` and `__newindex` callbacks originally traced both callbacks and print; decompiled output printed only `after`. `SelfAssignmentEliminator` now removes only local self-assignments; `ShortCircuitChainFolder::ExtractIdentifierName` returns a name only for local identifiers, guarding all its name-based folds. Focused test passes after fix (4 assertions, GCC Debug). Full suite pending.

### C10 — short-circuit diamond fold may substitute fallback for a false primary (`candidate`)

`ShortCircuitFolder::TryFoldAt` rewrites a declaration and branch diamond into `C and P or F` (`ShortCircuitFolder.hpp:99-128`). `ShortCircuitChainFolder::FoldTerminalMixedAndOrAt` makes the same replacement for a more specific terminal-return shape and runs earlier (`ShortCircuitChainFolder.hpp:442-545`; `Decompiler.cpp:833-862`). Luau `and/or` selects `F` when `P` is false/nil. The matched original branch assigns `P` in its true arm and may reach later statements with `P` still false; neither fold proves `P` truthy. Need show a compiler-produced bytecode and public decompiler output reaching either pass; then trace false/nil `P`. If reachable, test parity and fold only when `P` is proven truthy or construct an if-expression preserving false values.

**Directed probes:** A compiled function with early return on fallback and false primary decompiled to a simple `if`/return sequence. VM parity passed and the suspected fold did not trigger; that probe was removed from the permanent suite. A direct AST fixture can make the terminal fold return 7 instead of false for `c=true,p=false,f=7`, but the matching compiler-produced public shape remains unproven. A trial rewrite to `if C then P else F` broke two established compiler-produced short-circuit regressions, so that change and its direct-AST test were removed. Keep C10 open until a compiler-produced counterexample establishes the required control-flow shape and correct fix.

**Further source/probe check:** Compiler terminal-return arms omit a join jump (`Compiler.cpp:3793-3806`); ASTLifter treats the return arm as terminal and produces a one-sided if/continuation, while the terminal folder requires both branches. A nonterminal source with duplicated `print(v)` tails and `p=false` compiled at O0/O1/O2; fresh CLI output preserved the `if/else` at O0/O1 and produced an O2 branch that prints `false` once for the supplied constants. It did not trigger the unsafe fold. The direct-AST hazard remains; no compiler-reachable divergence is established.

**Rejected guard, compiler-backed red/green:** Direct AST fixtures for both folders did show `false`/`nil` primary values becoming fallback `7`. Guarding folds unless the primary was statically truthy made these fixtures pass, but broke two compiler-produced short-circuit regressions. A new compiler/VM parity test with `(a and b) and c or d`, called with `a=b=true,c=false,d=7`, showed the guarded output returned `false` rather than `7` (one failed trace assertion). Removing the guard restored parity at O0/O1/O2 (12 focused assertions; full CTest 629/629). These compiler shapes need the fold to restore their fallback edge; the same AST pattern is ambiguous without bytecode provenance. The direct-AST tests were removed. Keep the compiler-produced semantic test, and do not apply an AST-only truthiness restriction without repairing earlier reconstruction of the missing fallback path.

**Explicit-source follow-up:** Compiled `local v; if not c then v=f; return v else v=p; if v then return v end end; return v` with calls using false and truthy primaries. Semantic oracle matched (`false`, `8`, `5`); post-rewrite AST at O1 had a one-sided early-return `if`, then a separate assignment and conditional return. Luau omitted the branch join because the first arm terminates (`Compiler.cpp:3793-3806`), so neither diamond folder matched. No compiler-produced counterexample for the direct-AST hazard yet.

### C12 — if-expression fold coalesces global writes (`source-consistent`)

`IfExpressionFolder::AsIfExpr` matches two assignments by target name, then `Fold` replaces them with one assignment of an if-expression (`IfExpressionFolder.hpp:125-193`). ### C13 — bounded CFA loop-exit tracing (`candidate`)

`ControlFlowAnalyzer::IdentifyStructuresInternal` follows at most eight post-latch jump/NOP bridges when locating a loop exit (`ControlFlowAnalyzer.cpp:585-614`), at most sixteen single-successor blocks when joining exits after O2 inlining (`:619-664`), and at most eight jump/NOP blocks when classifying a forward jump as `continue` (`:1211-1234`). `BytecodeBuilder::foldJumps` may collapse ordinary jump chains; compiler output can still contain intervening non-collapsible blocks. Need derive a compiler-produced loop with a longer chain before calling these caps a defect. An unbounded graph walk with visited-set would be the narrow fix only if a counterexample reaches a cap.

**Directed probe:** Ten nested `if/else` arms around a `repeat` at O0 and O1 produced many branch blocks. The O0 post-latch exit was directly visible to `exitAt`; O1 jump folding produced return blocks. Both decompiled successfully with the same apparent branch and loop behavior. This does not exercise any hop cap and is not a regression test.

### C14 — repeat exit fallback selects unrelated return (`candidate`)

When a repeat latch has no identified exit, `ControlFlowAnalyzer.cpp:1084-1117` scans *all* basic blocks and assigns the first `Return`, without checking reachability from the repeat condition. Compiler `compileStatRepeat` emits condition branching over a `JUMPBACK` to post-loop code (`Compiler/src/Compiler.cpp:3873-3973`); ASTLifter trusts recorded non-latch exits (`ASTLifter.cpp:1598-1607`). This fallback is suspicious, but a compiler-produced route into it remains unproved. Do not change it without a red example.

**Directed probe:** Luau-compiled `if early then return 1 end; repeat until cond; print('after'); if flag then print('flag') end; return 2` inside a function decompiled to the same control flow. Original and output both printed `after` and returned 2 for `early=false,cond=true,flag=false` (GCC Debug, 4 assertions). The source-level fallback concern did not produce a behavior mismatch in this shape; the temporary test was removed.

**Source follow-up:** Luau places the normal repeat exit at `skipLabel` after `JUMPBACK` (`Compiler.cpp:3947-3968`); CFA usually finds it from escaping successors or `exitAfterLatch` (`ControlFlowAnalyzer.cpp:583-614,732-747`). The global first-`Return` fallback remains suspect if those routes fail, but no compiler-produced route to that failure was found. Do not remove the prior `c587d2702` header-successor guard without a red case; it protects compound conditions.

**Structural follow-up:** Compiled six repeat shapes with an earlier guard `return`, a post-loop `print` and final `return`, at O0/O1/O2: empty body; printed body; `or` exit; `and` exit; `break`; `continue`. For every shape CFA classified as repeat, its `loopExit` began after the latch, never at the earlier guard return (117 passing assertions in temporary probe). `repeat until cond and other` was emitted as equivalent `while true do if cond and other then break end end`, so a requirement that it retain the repeat classification was invalid. No C14 counterexample found; temporary probe removed rather than retaining a shape smoke test.

### C15 — inlining treats global lookup as effect-free (`fixed`)

Luau's `GETGLOBAL` slow path calls `luaV_gettable`, which can run `__index` or throw (`VM/src/lvmexecute.cpp:395-424`). `GETIMPORT` also calls `luaV_getimport` when safeenv is invalid; even a one-part import calls `luaV_gettable` (`lvmexecute.cpp:491-510`, `lvmload.cpp:90-122`). Fission's `ASTLifter::CanOperationRaise` omitted `GETGLOBAL` (`ASTLifterInlining.cpp:1245-1277` before fix), and `IsBareImport` marked one-part `GETIMPORT` non-raising (`:20-23` before fix). `ShouldInlineImpl` could then move a single-use lookup into its consumer without running `InliningReordersEffect` (`:547-595,627-642`). `LiftControlFlow` also uses `CanOperationRaise` when judging shared-tail effects (`ASTLifter.cpp:974-980,1125-1142`). First wrong stage: AST inlining's effect classifier.

**Red/green:** Compiler-produced one-part `GETIMPORT` for `local x=watched; trigger(); return x` under an environment `__index` callback read `watched` while state was 0. Before fix Fission emitted `trigger(); return watched`, reading after state became 1 (GCC Debug, 1 failed trace assertion). `CanOperationRaise` now includes `GETGLOBAL`, and the bare-import exception was removed from both inlining and statement-effect checks. Fission retains the lookup before `trigger()`. Extended focused test proves both compiler-emitted `GETIMPORT` and `GETGLOBAL` variants keep callback order and return value (GCC Debug, 12 assertions). Integration exposed an O2 closure whose captured register was later reused for `print`; a VM red test failed until REF capture lifetime received a distinct SSA name. It also exposed a call-callee lookup sharing its register name with its result; lookup naming now splits only that direct call use, and `ChildLookupRenamer` recognizes a preceding `require` alias. Existing short-circuit/constructor tests now assert their actual invariants without requiring direct `print(...)` spelling. Focused regressions pass; full suite rerun pending.

### C17 — normalized v1 parameter types are ignored (`fixed`)

### C18 — dead table literal with NaN key loses its runtime error (`fixed`)

Full suite pending.

### C19 — `CLOSEUPVALS` may hide a multret return producer from SSA (`source-consistent`)

Compiler `compileStatReturn` emits the final multret call/vararg producer, then `closeLocals(0)`, then `LOP_RETURN B=0` (`Compiler/src/Compiler.cpp:3995-4045`). If an active local was captured, `closeLocals` emits `LOP_CLOSEUPVALS` between producer and return (`:5025-5044`). Initial source review overlooked that `BytecodeLifter.cpp:1357-1367` lifts `CLOSEUPVALS` to `NOP` while separately recording its capture-lifetime marker. `VariadicTailCount` skips NOP (`SSABuilder.cpp:68-85`), so it still finds the multret producer. No missing tail count follows from this compiler shape.

**Directed probe:** Compiler emits `CALL; CLOSEUPVALS; RETURN` for `local x=1; local function capture() return x end; x=2; return 5, math.modf(3.5)`. Fission output retained `return 5, math.modf(3.5)` and both VMs returned `5, 3, 0.5` (GCC Debug, 8 assertions). The retained parity test covers this compiler shape. No SSA change needed.

### C20 — loop preparation can write registers absent from SSA defs (`source-consistent abstraction`)

VM `LOP_FORNPREP` can convert and overwrite its three numeric registers on the slow path (`VM/src/lvmexecute.cpp:2529-2541`); `LOP_FORGPREP_NEXT` and `LOP_FORGPREP_INEXT` can write A and A+2 on their fast paths (`:2811-2850`). Fission's source-oriented SSA models prep reads but does not model these conditional, VM-internal writes (`SSABuilder.cpp:1-64,125-180`). The registers are loop-protocol scratch: ASTLifter reconstructs generic-for initializers from values *before* prep (`ASTLifter.cpp:2501-2589`), and the numeric-for header must retain its original expressions. Unconditionally inserting prep defs would be inaccurate on the paths where VM does not write. No compiler-produced source-output divergence found. Keep this as a documented abstraction; reopen if an observable use outside loop protocol is demonstrated.

### C21 — computed table fields can truncate a trailing variadic list (`fixed`)

Luau `compileExprTable` flushes fixed list chunks before keyed items, then emits `SETLIST` with `C=0` for a final multret expression (`Compiler.cpp:2809-2857`). `ASTLifter::delayedVariadicSetList` rebuilds a local table at that final store to preserve all results. It rejected a computed key when a value call intervened between key call and `SETTABLE`: `storeSiteSnapshotableKey` allowed only `LOAD`/`NOP` in that interval (`ASTLifter.cpp:2770-2785` before fix). If an earlier computed key's register was later reused, `computedField` also rejected it. The generic `SETLIST` fallback then emitted `t[index] = ...`, which takes only the first variadic result. First wrong stage: AST lifting's key-snapshot eligibility, not compiler emission or SSA.

**Red/green:** Compiler-produced `{[key()] = value(), 10, [key()] = value(), ...}` called with `(10, false)` returned `t[3] == false`; decompiled output returned `nil` at O0/O1 (2 failed trace assertions). A materialized key call can safely be snapshotted at the store after intervening value calls: the key expression is already evaluated and its register's SSA version identifies the stored value. `storeSiteSnapshotableKey` now accepts that case when `ShouldInline(definition)` is false, preserving the earlier call order and letting delayed `SETLIST` reconstruction retain the full tail. Focused test passes at O0/O1/O2 with empty and nil-containing varargs and a call-produced multret tail (12 assertions); full CTest 630/630 and stress samples 22/22. No fuzzing run per analysis-first instruction.

**Global-key follow-up:** `{[keyA] = value(), 10, [keyB] = value(), ...}` also lost the second variadic result at O0/O1/O2 (3 failed trace assertions). Both global reads were already materialized before their stores, but `storeSiteSnapshotableKey` limited eligibility to call definitions. It now accepts any same-block, already-materialized key definition; only inlinable call definitions still need the intervening-instruction restriction. Both distinct regression cases pass (24 assertions), full CTest 631/631 and stress samples 22/22. This extends the same snapshot root cause rather than introducing a second table rewrite.
